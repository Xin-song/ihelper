## 一、产品定位

**iHelper 是一个自托管优先的个人与家庭数据中枢。**

一句话：把「我的日程、我的待办、我家的库存、我家的菜谱、我们的生活记录」放进同一套数据模型里，让它们能互相引用、互相触发。

区别于市面上的单点工具（Todoist 管待办、Notion 管笔记、各种记账 App 管消耗品），iHelper 的核心价值在**模块间的联动**：

- 菜谱 → 自动扣减食材库存 → 库存低于阈值 → 生成采购待办 → 待办出现在日程里
- 家庭事项 → 拆成多人待办 → 完成后沉淀为生活记录

如果最终产品做不到这种联动，那它就没有存在意义 —— 这是衡量所有功能取舍的第一原则。

## 二、长期愿景（12–24 个月）

| # | 目标 | 成功判据 |
|---|------|---------|
| L1 | 云端多租户服务 | 支撑 1000+ 注册用户、200+ 家庭空间，P95 响应 < 300ms |
| L2 | 真正的多平台 | Web + iOS + Android，移动端可离线读写并自动同步 |
| L3 | 模块联动闭环 | 上文描述的「菜谱→库存→采购→日程」链路全线打通 |
| L4 | 数据主权 | 用户可一键导出全部数据（JSON/CSV），可自建实例，无锁定 |
| L5 | 家庭协作 | 家庭空间内多成员共享数据，细粒度权限与操作审计 |

### 非目标（明确不做）

写清楚不做什么，比写做什么更能防止项目失控：

- ❌ 不做通用社交网络（无关注/粉丝关系链、无算法推荐信息流）
      —— 注意与「菜谱广场 / 交作业」的区别：那是围绕菜谱内容的分享与互动，
      按内容而非按人组织，时间倒序而非推荐排序。定位是「自用为主，顺带分享」。
- ❌ 不做记账/财务管理（范围太大，且已有大量成熟产品）
- ❌ 不做 IM 即时通讯
- ❌ 不做企业版 / 团队协作版
- ❌ 初期不做 AI 功能（等数据模型稳定后再谈，避免过早引入复杂度）

## 三、短期目标（未来 3 个月）

**唯一目标：把菜谱模块做成一个自己每周都会用的完整产品。**

不是做一个「能跑通的 demo」，而是做一个「不用它反而不方便」的东西。理由：

1. 菜谱是所有模块里**数据结构最复杂**的（菜谱 ↔ 食材 ↔ 单位换算 ↔ 分量缩放），先啃硬骨头，后面的库存、待办在结构上都是它的子集
2. 菜谱是**唯一不依赖其他模块**就能独立产生价值的模块
3. 菜谱天然连接库存（食材）和日程（做饭计划），是联动链路的中心节点

### 3 个月内的验收标准

- [ ] 录入 ≥ 30 道自家常做的菜，且录入过程不觉得繁琐（单道菜 < 3 分钟）
- [ ] 手机浏览器上能顺畅查看菜谱（做饭时单手看，字够大，不误触）
- [ ] 分量缩放可用：2 人份一键换算成 4 人份
- [ ] 选中几道菜 → 自动合并生成购物清单
- [ ] 本地 Docker 一条命令启动，数据可备份可恢复

## 四、阶段划分

### Phase 0 — 项目奠基 ✅

**周期**：1–2 周　|　**目标**：能开始写业务代码

- [x] 明确需求与目标（本文档 + REQUIREMENTS.md + ARCHITECTURE.md）
- [ ] GitHub 仓库初始化，确定分支策略与提交规范
- [x] Monorepo 骨架：`apps/web`（Vue）+ `apps/api`（NestJS）+ `packages/shared`（共享类型，CJS + ESM 双构建）
- [ ] Docker Compose 一键启动开发环境（含 PostgreSQL）—— `db` 服务已就绪，`api`/`web` 容器化待做
- [x] 数据库 Schema 首版 + 迁移工具跑通（菜谱模块，详见 [DATABASE.md](./DATABASE.md)）
- [ ] CI：提交即跑 lint + 类型检查 + 测试

**退出条件**：`git clone` 后执行一条命令，浏览器能打开一个连着数据库的空白页面。
　→ 已达成（`pnpm db:up` + `api:dev` + web `dev`，页面能读写真实数据）。剩下的是把
　　 `api`/`web` 也塞进 compose，让「一条命令」名副其实。

---

### Phase 1 — 菜谱 MVP 🟨

**周期**：4–6 周　|　**目标**：短期目标的验收标准全部打勾

- [ ] 单用户登录（账号密码，会话管理）
- [x] 食材主数据：名称、别名、默认单位、分类
- [x] 菜谱 CRUD：标题、图片、分类/标签、配料表、步骤、耗时、份数
- [x] 图片上传（封面 / 作业成品图 / 打印版），本地磁盘 + 可替换的存储抽象层
- [ ] 单位换算体系（g / kg / ml / 个 / 勺 / 适量）—— 精确/模糊两种用量已分开建模，换算表待做
- [x] 分量缩放
- [ ] 搜索与筛选：按名称、标签、食材反查（「有鸡蛋能做什么」）
- [ ] 购物清单：多选菜谱 → 合并同类项 → 可勾选/导出
- [ ] 移动端响应式布局 + 做饭模式（大字、防熄屏、步骤逐条）
- [x] 可打印菜谱图：按菜谱数据 Canvas 排版生成 A4 图，也可上传自己的横版/竖版
- [ ] 数据导入导出（JSON）

**退出条件**：连续两周真实使用，不再需要打开其他菜谱 App。

---

### Phase 2 — 库存与待办 ⬜

**周期**：4–6 周　|　**目标**：跑通第一条联动链路

- [ ] 消耗品库存：数量、单位、保质期、存放位置、低库存阈值
- [ ] 耐用品台账：购入日期、价格、保修期、说明书附件
- [ ] 「做了这道菜」→ 按配料表扣减库存
- [ ] 低库存/临期自动生成采购待办
- [ ] 待办模块：标题、截止时间、优先级、重复规则、标签
- [ ] 简易日程视图（日/周/月），待办按截止日落在日历上

**退出条件**：完整走通一次「查菜谱 → 做饭 → 库存自动减 → 提醒买菜 → 买完补库存」。

---

### Phase 3 — 家庭空间与多用户 ⬜

**周期**：4–6 周　|　**目标**：从单用户升级为家庭共享，且不推翻已有数据

- [ ] 引入 `space` 概念，所有业务表补 `space_id`（详见 ARCHITECTURE.md 的迁移方案）
- [ ] 邀请成员加入家庭空间
- [ ] 角色：管理员 / 成员 / 只读
- [ ] 家庭事项：可指派给成员，进度可见
- [ ] 数据可见性：个人私有 vs 空间共享
- [ ] 操作审计日志

**退出条件**：家人真的在用，且不需要你在旁边解释怎么用。

---

### Phase 4 — 生活记录 ⬜

**周期**：3–4 周

- [ ] 图文日记 / 动态，支持多图
- [ ] 图片存储抽象层（本地磁盘 ↔ S3 兼容对象存储可切换）
- [ ] 时间线与按时间/标签检索
- [ ] 空间内成员可见、可评论
- [ ] 与其他模块关联（把某次做饭、某个完成的家庭事项存成记录）

---

### Phase 5 — 上云与多平台 ⬜

**周期**：持续

- [ ] 生产环境部署（反向代理、HTTPS、自动备份、监控告警）
- [ ] 性能：索引优化、查询分析、缓存层
- [ ] PWA：可安装、离线只读
- [ ] 移动端 App（技术方案在 Phase 4 结束前评估决定）
- [ ] 端到端同步与冲突解决

## 五、跨阶段的持续要求

这些不属于某一个阶段，而是每个阶段都要满足：

- **每个 Phase 结束时**，本文档与 REQUIREMENTS.md 必须同步更新
- **数据库变更一律走迁移文件**，禁止手改生产库
- **每个 Phase 至少一次数据备份恢复演练**，验证备份真的能恢复
- **API 保持版本化**（`/api/v1/...`），为将来的移动端留出兼容空间
- **共享类型定义单点维护**，前后端不各写一份
