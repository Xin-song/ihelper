iHelper 项目看板

个人与家庭数据中枢 · 最后更新 2026-07-28

核心价值是模块间的联动，不是功能的数量。
菜谱 → 扣减食材库存 → 低于阈值 → 生成采购待办 → 出现在日程里。
如果最终产品做不到这条链路，它就没有存在意义 —— 这是所有功能取舍的第一原则。

阶段路线

▶ Phase 0 · 项目奠基1–2 周 进行中 17%
目标　能开始写业务代码
  • ✓明确需求与目标（三份文档）
  • GitHub 仓库初始化，确定分支策略与提交规范
  • Monorepo 骨架：apps/web + apps/api + packages/shared
  • Docker Compose 一键启动开发环境（含 PostgreSQL）
  • 数据库 Schema 首版 + 迁移工具跑通
  • CI：提交即跑 lint + 类型检查 + 测试
退出条件　git clone 后执行一条命令，浏览器能打开一个连着数据库的空白页面。
▶ Phase 1 · 菜谱 MVP4–6 周 未开始 0%
目标　做一个「不用它反而不方便」的菜谱工具，不是 demo
  • 单用户登录（账号密码，会话管理）
  • 食材主数据：名称、别名、默认单位、分类
  • 菜谱 CRUD：图片、标签、配料表、步骤、耗时、份数
  • 单位换算体系（g / kg / ml / 个 / 勺 / 适量）
  • 分量缩放（含智能取整：1.33 个 → 约 1½ 个）
  • 搜索与筛选，含食材反查「有鸡蛋能做什么」
  • 购物清单：多选菜谱 → 合并同类项 → 导出
  • 做饭模式：大字、防熄屏、步骤逐条、可计时
  • 数据导入导出（JSON）
退出条件　连续两周真实使用，不再需要打开其他菜谱 App。录入 ≥30 道菜，单道 <3 分钟。
▶ Phase 2 · 库存与待办4–6 周 未开始 0%
目标　跑通第一条联动链路
  • 消耗品库存：数量、保质期、存放位置、低库存阈值
  • 耐用品台账：购入日期、价格、保修期、说明书附件
  • 「做了这道菜」→ 按配料表扣减库存
  • 低库存 / 临期自动生成采购待办
  • 待办：截止时间、优先级、重复规则、子任务
  • 日程视图（日/周/月），待办按截止日落在日历上
退出条件　完整走通一次「查菜谱 → 做饭 → 库存自动减 → 提醒买菜 → 补库存」。
▶ Phase 3 · 家庭空间与多用户4–6 周 未开始 0%
目标　从单用户升级为家庭共享，且不推翻已有数据
  • 启用 space 概念（Phase 1 已在表结构中预留 space_id）
  • 邀请成员加入家庭空间
  • 角色：管理员 / 成员 / 只读
  • 家庭事项：可指派给成员，进度可见
  • 数据可见性：个人私有 vs 空间共享（私有数据管理员亦不可见）
  • 操作审计日志
退出条件　家人真的在用，且不需要你在旁边解释怎么用。
▶ Phase 4 · 生活记录3–4 周 未开始 0%
目标　把日常沉淀下来，并与其他模块互相引用
  • 图文日记 / 动态，支持多图
  • 图片存储抽象层（本地磁盘 ↔ S3 兼容可切换）
  • 时间线与按时间 / 标签检索
  • 空间内成员可见、可评论
  • 关联其他模块（某次做饭、某个完成的家庭事项）
▶ Phase 5 · 上云与多平台持续 未开始 0%
目标　1000+ 用户的云端服务 + 真正的多平台
  • 生产部署：反向代理、HTTPS、自动备份、监控告警
  • 性能：索引优化、查询分析、缓存层（API P95 < 300ms）
  • PWA：可安装、离线只读
  • 移动端 App（技术方案在 Phase 4 结束前评估）
  • 端到端同步与冲突解决

明确不做

社交网络 记账 / 财务管理 即时通讯 企业版 / 团队协作 初期的 AI 功能

待决事项

后端框架：NestJS（推荐）还是 FastAPI？
前端已定 Vue + TS。全栈同语言可共享类型定义，对单人长期项目是决定性优势 · 需在 Phase 0 开始前定
UI 组件库：Naive UI 还是 Element Plus？
Phase 0 各搭一个原型页面试用后再定
模糊单位（「一勺」「适量」）如何建模？
最容易过度设计的地方。第一版明确不做密度换算 · Phase 1 设计阶段定
移动端技术路线：PWA / React Native / Capacitor？
Phase 4 结束前评估，届时对使用场景的认识会比现在清楚得多
